# research-term

용어 하나를 조사해 **출처가 붙은 보고서**를 만든다. 위키 등록은 `write-wiki` 의 일이므로 여기서는 `terms/` 를 수정하지 않는다.

## 입력

- 키워드 (필수): 예) `MCP`, `prompt caching`
- 맥락 (선택): 어느 카테고리/상황에서 쓰이는 말인지. 동음이의어 구분에 쓴다.

키워드가 여러 의미로 갈리고 맥락도 없으면, 가장 흔한 코딩 에이전트 의미로 진행하고 가정으로 보고서에 적는다.

## 1단계: 사용 가능한 조사 수단 파악

세션의 스킬·도구 목록에서 검색/가져오기 수단을 모두 확인한다.

1. **ego-browser 스킬이 있으면 우선 사용.** 로그인된 브라우저로 공식 문서·논문·표준 사이트를 직접 열어 읽는다. 사용법은 해당 스킬의 SKILL.md 를 먼저 읽고 따른다.
2. WebSearch / WebFetch.
3. 그 외 목록에 있는 search·fetch·문서 조회 성격의 스킬이나 MCP (예: context7, chub, external-context, document-specialist 계열).
4. 이 레포의 기존 `terms/` (중복·관련 용어 파악용, `ask-wiki` 방식으로 grep).

없는 수단은 건너뛴다. 하나도 없으면 보고서에 "조사 수단 없음"이라고 쓰고 멈춘다.

## 2단계: 병렬 조사

독립적인 질의는 **한 턴에 동시에** 보낸다. 여러 수단이 있으면 수단별로 서브에이전트를 나눠 동시에 돌린다.

질의 축:

| 축 | 찾을 것 | 우선 출처 |
| --- | --- | --- |
| 정의 | 공식 정의, 약어 풀이, 별칭 | 공식 문서, 스펙, 저자/제공사 블로그 |
| 동작 | 구조, 흐름, 최소 예시 | 공식 문서, GitHub 저장소 |
| 배경 | 왜 생겼나, 해결하는 문제, 대안 | 발표글, 논문, RFC |
| 에이전트 맥락 | 코딩 에이전트에서 쓰이는 방식 | Anthropic·OpenAI·Google 등 공식 문서 |
| 혼동 | 비슷한 용어와의 차이, 흔한 오해 | 공식 FAQ, 신뢰할 만한 기술 블로그 |

## 3단계: 출처 신뢰도 판정

- **A**: 공식 문서, 스펙/RFC, 저자·제공사 1차 자료, 동료 심사 논문
- **B**: 주요 기술 기업 블로그, 저명한 저자의 기술 글, 공식 저장소 README
- **C**: 개인 블로그, 포럼, 요약 사이트, 2차 재가공 글

정의·수치·버전 같은 핵심 주장은 A/B 출처 2곳 이상에서 확인한다. C 만 있는 주장은 "미확인"으로 표시한다. 출처끼리 충돌하면 숨기지 말고 둘 다 적는다. 검색 결과 요약만 보고 내용을 단정하지 말고, 핵심 출처는 페이지를 직접 열어 확인한다.

## 4단계: 보고서 출력

아래 형식으로 반환한다. `write-wiki` 가 그대로 파싱해 쓰므로 제목을 바꾸지 않는다.

```markdown
# 조사 보고서: <키워드>

- 조사일: YYYY-MM-DD
- 가정: <맥락 가정이 있었다면>
- 사용한 수단: <ego-browser / WebSearch / ...>

## 한 줄 정의
...

## 핵심 내용
- 정의/약어/별칭
- 왜 필요한가
- 어떻게 동작하나
- 최소 예시 (코드/명령/문장)
- 코딩 에이전트 맥락
- 흔한 오해·유사 용어

## 추천 카테고리
<development | video-generate | image-generate | legal | research | data-analysis | 새 카테고리 제안> — 근거 한 줄

## 관련 용어
- <용어> — 관계 한 줄 (이 레포에 이미 있으면 경로 표기)

## 미확인·충돌
- ...

## 출처
| # | 제목 | URL | 등급 | 확인한 내용 |
| --- | --- | --- | --- | --- |
```

## 하지 않는 것

- 위키 파일 생성·수정.
- 출처 없이 기억에서 채운 내용을 사실처럼 쓰기. 기억에 의존한 내용은 "기억 기반·미확인"으로 표시한다.
