# Architecture Decision Record

> 소프트웨어 시스템을 설계하거나 운영 정책을 정할 때 내린 중요한 기술적·구조적 의사결정과 그 배경, 대안, 결과를 짧은 문서로 남긴 기록.

## 요약

- ADR 은 Architecture Decision Record(아키텍처 결정 기록)의 약어다.
- 결정 하나당 짧은 문서 하나로, 결정 내용뿐 아니라 배경·대안·결과를 함께 남긴다.
- 주요 구성 요소는 제목 및 상태, 컨텍스트(Context), 결정(Decision), 결과(Consequences)다.
- 상태 예시는 Proposed, Accepted, Deprecated 다.
- 에이전트 작업에서는 세부 수치를 지금 하드코딩하지 않고, 근거와 함께 ADR 로 나중에 확정하는 용도로 쓰이기도 한다.

## 왜 필요한가

중요한 설계 결정은 결과값만 남으면 왜 그렇게 정했는지, 어떤 대안이 있었는지 알 수 없게 된다. ADR 은 결정과 함께 배경·대안·결과(이점과 트레이드오프)를 기록해 그 맥락을 보존한다. 값이 아직 확정되지 않았다면 규칙만 먼저 정하고 구체적인 값은 ADR 에서 근거와 함께 확정하는 방식도 가능하다.

## 어떻게 동작하나

한 건의 결정을 한 문서에 담고, 아래 요소로 구성한다.

| 요소 | 내용 |
| --- | --- |
| 제목 및 상태 | 결정 내용과 현재 상태 (예: Proposed, Accepted, Deprecated) |
| 컨텍스트(Context) | 어떤 문제나 상황 때문에 이 결정이 필요한지 (배경) |
| 결정(Decision) | 최종적으로 채택한 값이나 구조 |
| 결과(Consequences) | 이 결정으로 얻는 이점과 감수해야 할 트레이드오프 |

## 예시

원문의 맥락에서 쓰인 값(토큰 TTL 15분, 스냅샷 주기 24시간, 레이트 리밋 100 rps)을 ADR 골격에 놓으면 다음과 같다. 값은 원문이 든 예시이며 권장값이 아니다.

```markdown
# ADR: 토큰 TTL 과 레이트 리밋 기본값

- 상태: Proposed
- 컨텍스트: (이 값이 필요한 이유와 제약)
- 결정: 토큰 TTL 15분, 스냅샷 주기 24시간, 레이트 리밋 100 rps (확정 전)
- 결과: (이점과 트레이드오프)
```

## 에이전트 맥락

원문은 에이전트의 초기 기본값 설정 규칙(seed)에서 "수치 기본값을 반드시 명시해야 한다"는 규칙만 걸어 두고, 실제 운영 수치는 ADR 을 정식으로 작성하며 근거와 함께 최종 확정하겠다는 선택지를 설명한다. 이 선택지가 어떤 도구·워크플로의 화면에서 나왔는지는 원문에 없다 _(미확인)_.
