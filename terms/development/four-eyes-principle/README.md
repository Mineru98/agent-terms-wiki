# 4-eyes 원칙 (Four-eyes Principle)

> 중요한 작업은 한 사람이 단독으로 끝내지 못하고, 다른 한 사람이 독립적으로 확인하거나 승인해야 완료되도록 하는 통제 원칙.

## 요약

- 4-eyes 원칙은 "눈 네 개", 즉 두 사람이 확인한다는 뜻으로, 한 사람의 실수나 부정이 그대로 통과하는 일을 막는다.
- 작성하는 사람과 승인하는 사람을 분리하는 것이 핵심이다.
- 직무 분리(SoD, Separation of Duties)라는 더 넓은 개념의 한 형태로 설명된다.
- 코드 리뷰 승인, 운영 배포 승인, 결제 승인 같은 곳에서 쓰인다.

## 왜 필요한가

한 사람이 요청하고 승인까지 할 수 있으면, 실수는 걸러지지 않고 부정은 숨겨진다. 두 번째 사람이 독립적으로 확인하게 하면 단일 인물의 오류나 악의가 시스템 전체의 사고로 이어지는 경로를 끊는다.

## 어떻게 동작하나

1. 작업 수행자(요청자, 작성자)와 확인자(승인자)를 서로 다른 사람으로 지정한다.
2. 확인자는 작업 결과를 독립적으로 검토하고 승인 또는 반려한다.
3. 승인 전에는 작업이 확정되지 않는다. 시스템으로 구현할 때는 요청자 본인의 승인을 막는 규칙을 둔다.
4. 누가 요청하고 누가 승인했는지 기록을 남긴다.

Wikipedia 의 직무 분리 문서는 이를 분리 방식 네 가지 중 하나인 "개별 분리(individual separation)"로 소개한다. 순차 분리(두 서명 원칙), 공간 분리, 요인 분리와 같은 계열이다.

## 예시

GitHub 저장소의 브랜치 보호 규칙으로 "병합 전 승인 1건 필요, 작성자 본인 승인은 불인정"을 거는 구성이 대표적이다. 이 설정 항목의 정확한 이름은 조사하지 않아 미확인이다. 개념만 쓰면 다음과 같다.

```text
요청자 A: 운영 DB 스키마 변경 PR 작성
승인자 B: 변경 내용 검토 후 승인 (A 본인은 승인 불가)
배포: B 의 승인이 기록된 뒤에만 실행
```

## 에이전트 맥락

코딩 에이전트가 코드를 작성하고 같은 에이전트(또는 같은 맥락)가 승인까지 하면 4-eyes 가 성립하지 않는다. 작성 단계와 검토 단계를 다른 주체로 나누는 방식이 이 원칙의 적용이다. 에이전트 도구가 이를 어떻게 구현하는지는 조사하지 않아 미확인이다.

## 흔한 오해

- **4-eyes 와 직무 분리는 같은 말이 아니다.** 직무 분리는 한 업무를 여러 단계와 역할로 나누어 한 사람이 충분한 권한을 갖지 못하게 하는 넓은 원칙이다. NIST 는 어떤 사용자에게도 시스템을 단독으로 오용할 만큼의 권한을 주지 않는 원칙으로 정의한다. 4-eyes 는 그중 승인·확인 시점에 두 번째 사람을 요구하는 구체적 통제다. 직무 분리는 역할 정의(정적)로도 구현되고, 4-eyes 는 실행 시점의 확인(동적)에 해당하는 두 사람 규칙과 가깝다.
- **4-eyes 와 이중 통제(dual control)도 구분된다.** PCI 용어집의 dual control 은 둘 이상의 주체가 함께 움직여야만 암호 키 같은 민감한 자료에 접근할 수 있는 통제다. 4-eyes 는 확인 중심이고, dual control 은 두 사람이 함께 있어야 접근 자체가 가능하다는 점이 강조된다. 이 둘의 경계는 출처마다 다르게 쓰여 일부는 혼용한다.
- **두 사람이 보기만 하면 되는 것이 아니다.** 확인자가 형식적으로 승인하거나 요청자와 같은 권한 경로를 공유하면 효과가 없다.
