# Fan-out / Fan-in

> 하나의 작업을 여러 개로 나누어 병렬로 실행(Fan-out)하고, 그 결과를 다시 하나로 모아 통합하는(Fan-in) 구조.

## 요약

- Fan-out 은 작업을 여러 갈래로 분산해 동시에 시작하는 단계이고, Fan-in 은 갈래마다 나온 결과를 수집·종합하는 단계다.
- 코딩 에이전트에서는 메인 에이전트가 여러 서브 에이전트(sub-agent)를 동시에 실행하고 결과를 받아 합치는 멀티 에이전트 구성에서 자주 쓰인다.
- Fan-in 은 단순 병합이 아니라 결과 사이의 충돌·모순을 조정하는 과정까지 포함한다.
- 작업 사이에 의존성이 없을 때 소요 시간이 줄어든다. 다만 컨텍스트 중복, 토큰 비용, 파일 충돌 같은 부담이 따른다.
- AI 에이전트 전용 용어가 아니며 서버 아키텍처, 분산 시스템, 비동기 프로그래밍, 워크플로 오케스트레이션에서도 같은 개념으로 쓴다.

## 왜 필요한가

분석·조사·테스트 작성처럼 서로 독립적인 작업을 한 에이전트가 순차로 처리하면 전체 시간이 각 작업 시간의 합이 된다. Fan-out 으로 독립 작업을 동시에 진행하면 가장 오래 걸리는 작업 시간에 가까워진다. 갈라진 결과는 그대로는 쓸 수 없으므로, 이를 한 곳에 모아 일관된 결론으로 만드는 Fan-in 이 짝으로 필요하다.

## 어떻게 동작하나

| 구분 | Fan-out | Fan-in |
| --- | --- | --- |
| 의미 | 하나를 여러 개로 분산 | 여러 개를 하나로 통합 |
| 실행 방식 | 병렬 작업 시작 | 결과 수집 및 종합 |
| 주요 목적 | 작업 시간 단축 | 결과의 일관성 확보 |
| 에이전트 역할 | 작업을 위임 | 결과를 검토·통합 |

예상 소요 시간은 대략 다음과 같다 (작업 간 의존성이 없다고 가정).

```
T_parallel ≈ max(T_A, T_B, T_C) + T_merge
```

실제로는 서브 에이전트 생성, 컨텍스트 전달, 파일 충돌, 결과 검토에 추가 시간이 들어 반드시 빨라지는 것은 아니다.

Fan-out 을 늘릴 때 생기는 문제는 아래와 같다.

| 문제 | 설명 |
| --- | --- |
| Context 중복 | 각 에이전트가 같은 코드베이스를 반복해서 읽음 |
| Token 비용 증가 | 병렬 호출로 전체 토큰 소비가 증가할 수 있음 |
| 파일 수정 충돌 | 여러 에이전트가 같은 파일을 수정 |
| 작업 의존성 | A 의 결과가 있어야 B 를 시작할 수 있음 |
| Fan-in 병목 | 메인 에이전트의 검토·통합 작업이 복잡해짐 |

일반적으로 조사·분석·리뷰처럼 독립성이 높은 작업을 Fan-out 하고, 코드 수정과 통합 검증은 의존성과 파일 소유권을 고려해 조정하는 편이 안전하다고 설명된다. 특히 같은 파일의 수정 권한을 여러 에이전트에게 동시에 주는 것은 주의해야 한다.

## 예시

요청: "현재 프로젝트의 인증 시스템을 분석하고, 보안 취약점을 찾아 수정한 다음 테스트까지 진행해 줘."

1. **Fan-out**: 메인 에이전트가 서브 에이전트 셋을 동시에 실행한다.
   - Agent A: 기존 인증 시스템의 코드와 구조 분석
   - Agent B: 인증 API 테스트 케이스 조사 및 작성
   - Agent C: JWT, 세션, 권한 검증의 보안 취약점 조사
2. **Fan-in**: 메인 에이전트가 A 의 아키텍처 분석, B 의 테스트 코드·검증 결과, C 의 취약점 분석을 수집한다. 이를 종합해 수정 계획을 세우고 코드를 변경한 뒤 최종 테스트를 수행한다.

소요 시간 예시 (가상 수치): A 10분, B 15분, C 8분, 통합 3분이라면 순차 실행은 10+15+8+3 = 36분, 병렬 실행은 max(10,15,8)+3 = 18분으로 약 50% 단축된다. 원문에서 "이론적 예시"로 제시한 값이며 실측이 아니다.

## 에이전트 맥락

Claude Code, Codex 같은 코딩 에이전트가 여러 서브 에이전트를 동시에 실행하는 멀티 에이전트 환경에서 등장한다. 메인 에이전트는 오케스트레이터(orchestrator) 역할로 작업을 위임하고, 결과를 모아 충돌을 조정한 뒤 다음 단계를 진행한다. 원문은 관련 개념으로 필요한 작업이 모두 끝날 때까지 다음 단계로 넘어가지 않는 지점(동기화 지점, synchronization barrier)을 함께 든다.

## 흔한 오해

- **"Fan-out 을 많이 할수록 좋다"**: 의존성이 있거나 같은 파일을 건드리는 작업, Fan-in 이 복잡해지는 경우에는 오히려 비용과 충돌이 늘 수 있다.
- **"Fan-in 은 결과를 이어 붙이는 일이다"**: 결과 사이의 충돌·모순을 조정하는 과정이 포함된다.
- MapReduce 는 분산 처리 후 집계하는 대표적 패턴으로, 구조가 Fan-out/Fan-in 과 유사하다고 설명된다. 같은 용어는 아니다.
