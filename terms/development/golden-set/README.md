# Golden Set

> 코딩 에이전트가 작업을 제대로 수행하는지 평가하기 위해 미리 준비해 둔, 검증된 테스트 문제와 정답 판정 기준의 모음.

## 요약

- 골든셋은 에이전트용 "모의고사 문제집 + 채점 기준표"에 해당한다.
- 각 테스트 케이스는 Input(작업), Environment(코드·실행 환경), Expected Outcome(기대 결과), Constraints(제약), Evaluator(판정 방법)로 구성된다.
- 에이전트·프롬프트·설정·도구를 바꿨을 때 이전보다 나아졌는지, 기존에 되던 작업이 깨지지 않았는지를 같은 문제 집합으로 비교하는 데 쓴다.
- 정답 코드와의 일치 여부보다 테스트 통과, 동작 결과, 보안 제약 같은 결과 기준으로 채점하는 경우가 많다.
- 골든셋의 가치는 문제 수가 아니라 검증된 정답 기준에 있다.

## 왜 필요한가

에이전트가 "완료했습니다"라고 보고해도 실제로는 요구한 동작만 고치고 정상 경로를 깨뜨리거나, 기존 테스트를 삭제해 통과시키거나, 무관한 코드를 대량으로 바꿨을 수 있다. 코드가 수정됐는지만 보면 이런 경우를 잡지 못한다. 골든셋은 요구사항 충족, 기존 기능 유지, 제약 준수를 같은 기준으로 반복 측정해 "잘하는 것 같다"는 인상을 "30개 중 27개 성공" 같은 수치로 바꾼다.

## 어떻게 동작하나

1. 대표 작업 여러 개를 골라, 각 작업에 환경과 기대 결과·제약·판정 방법을 붙여 골든셋으로 만든다.
2. 에이전트에는 작업 지시와 프로젝트 환경만 준다. 기대 결과는 평가 시스템이 별도로 보관한다.
3. 평가 시스템이 에이전트의 결과물을 실행·채점한다. 기존 단위·통합 테스트를 채점 도구로 쓸 수 있다.
4. 변경 전후(예: 기존 프롬프트 vs 개선 프롬프트)를 동일 환경에서 비교하고, 기존에 성공하던 작업이 실패하지 않았는지도 확인한다.

일반 테스트와 비교하면 다음과 같다.

| 구분 | 일반 테스트 | 골든셋 |
| --- | --- | --- |
| 목적 | 소프트웨어 기능 검증 | 에이전트 수행 능력 평가 |
| 대상 | 코드의 동작 | 작업 지시부터 결과까지 |
| 입력 | 함수 인자, HTTP 요청 등 | 자연어 지시 + 코드베이스 |
| 결과 | 테스트 성공/실패 | 작업 성공률, 회귀 발생 여부 등 |
| 활용 | CI/CD, 배포 검증 | 모델·프롬프트·도구 변경 비교 |

## 예시

JSONL 한 줄에 해당하는 케이스 하나를 JSON 으로 풀어 쓴 예다.

```json
{
  "id": "AUTH-001",
  "task": "잘못된 비밀번호 입력 시 401 반환",
  "repository": "backend-api",
  "expected": {
    "wrong_password_status": 401,
    "correct_password_status": 200,
    "existing_tests_pass": true
  },
  "constraints": [
    "기존 인증 기능 유지",
    "테스트 코드 삭제 금지"
  ]
}
```

프로젝트 안에서는 아래처럼 두는 구성이 제안된다.

```
project/
├── src/
├── tests/
└── evals/
    ├── golden/
    │   ├── bugfix.jsonl
    │   ├── feature.jsonl
    │   ├── refactor.jsonl
    │   └── security.jsonl
    ├── evaluator.py
    └── results/
```

## 에이전트 맥락

Claude Code, Codex 같은 코딩 에이전트를 쓰는 프로젝트에서 다음 질문에 답하는 데 쓴다.

- `CLAUDE.md` 를 바꿨을 때 실제 코드 품질이 좋아졌는가?
- Claude Code 와 Codex 중 우리 프로젝트의 버그 수정에 더 맞는 쪽은 무엇인가?
- 새 MCP 도구를 추가했을 때 작업 성공률이 올랐는가?
- 버그는 고쳤지만 기존 기능을 깨뜨리지 않았는가?

과거에 에이전트가 실패한 실제 개발 작업을 골든셋에 추가하면 같은 문제가 재발하지 않는지 계속 확인할 수 있다.

## 흔한 오해

- **골든셋 = 정답 코드가 아니다.** 같은 버그도 고치는 방법이 여러 가지라서, 정답 코드와의 일치보다 테스트 통과·동작 결과·제약 준수를 기준으로 삼는 경우가 많다.
- **문제 수가 많으면 좋은 골든셋이 아니다.** 임의의 작업 100개를 모은 것만으로는 신뢰할 수 없고, 검증된 정답 기준이 있어야 한다.
- **일반 테스트를 대체하지 않는다.** 단위·통합 테스트는 골든셋의 채점 도구로 쓰인다.
- **비슷한 세 용어를 구분한다.**

| 용어 | 답하는 질문 | 내용 |
| --- | --- | --- |
| 골든셋(Golden Set) | 무엇으로 평가할 것인가 | 검증된 문제와 정답 기준 |
| 평가 시스템(Eval Harness) | 어떻게 평가할 것인가 | 실행, 테스트, 채점 자동화 |
| 벤치마크(Benchmark) | 성능을 어떻게 비교할 것인가 | 공통 평가 과제와 측정 결과 |

## 관련 용어

_(등록된 관련 용어 없음)_ — Eval Harness, Benchmark 는 아직 위키에 없다.
