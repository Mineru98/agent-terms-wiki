\*\*골든셋(Golden Set)\*\*은 코딩 에이전트가 작업을 제대로 수행하는지 평가하기 위해 미리 준비해 둔 검증된 테스트 문제와 정답 기준의 모음입니다.

쉽게 말하면, 코딩 에이전트 전용 모의고사 문제집 + 채점 기준표라고 생각하면 됩니다.

Claude Code, Codex 같은 코딩 에이전트를 개선하거나 설정을 변경했을 때, 이전보다 코딩을 잘하는지 객관적으로 판단하는 데 사용합니다.

## 1. 골든셋은 왜 필요할까?

예를 들어 코딩 에이전트에게 다음과 같이 지시했다고 가정해 보겠습니다.

> "사용자 로그인 API에서 잘못된 비밀번호를 입력하면 HTTP 401을 반환하도록 수정해."

에이전트가 코드를 수정하고 "완료했습니다"라고 답했습니다.

그런데 실제로는 다음과 같은 문제가 생길 수 있습니다.

- 잘못된 비밀번호에 대해서는 401을 반환하지만 정상 로그인이 실패함
- 기존 테스트 코드를 삭제해 테스트를 통과시킴
- 필요 없는 인증 관련 코드를 대량으로 변경함

이때 골든셋을 사용하면 단순히 코드 수정 여부만 보는 것이 아니라 실제로 요구사항을 만족하면서 기존 기능도 유지했는지 평가할 수 있습니다.

## 2. 골든셋의 구조

하나의 골든셋에는 여러 테스트 케이스가 들어갑니다.

| 구성 요소            | 설명             | 예시             |
| ---------------- | -------------- | -------------- |
| Input            | 에이전트에 주어지는 작업  | 로그인 API 버그 수정  |
| Environment      | 작업할 코드 및 실행 환경 | FastAPI 프로젝트   |
| Expected Outcome | 기대하는 결과        | 잘못된 비밀번호 → 401 |
| Constraints      | 지켜야 할 제약       | 기존 정상 로그인 유지   |
| Evaluator        | 결과를 판단하는 방법    | pytest 및 코드 검증 |

골든셋을 이용한 평가 과정

골든셋

검증된 작업 30개 + 정답 판정 기준

에이전트 A

기존 프롬프트

# 21/30

70% 통과

에이전트 B

개선된 프롬프트

# 27/30

90% 통과

동일한 환경에서 평가 결과 비교

기존에 성공하던 작업이 실패하지 않는지도 확인

위 숫자는 개념 설명을 위한 가상 예시입니다.

## 3. 실제 골든셋 예시

JSON으로 관리한다면 다음처럼 구성할 수 있습니다.

```
{
  "id": "AUTH-001",
  "task": "잘못된 비밀번호 입력 시 401 반환",
  "repository": "backend-api",
  "expected": {
    "wrong_password_status": 401,
    "correct_password_status": 200,
    "existing_tests_pass": true
  },
  "constraints": [
    "기존 인증 기능 유지",
    "테스트 코드 삭제 금지"
  ]
}
```

에이전트에게는 작업 지시와 필요한 프로젝트 환경을 제공하고, 평가 시스템은 별도로 보관한 기대 결과를 기준으로 채점합니다.

중요한 점은 골든셋이 반드시 정답 코드 자체를 의미하지는 않는다는 것입니다.

동일한 버그를 수정하는 방법은 여러 가지일 수 있으므로, 코딩 에이전트에서는 정답 코드와 정확히 일치하는지보다 테스트 통과, 동작 결과, 보안 제약 등을 기준으로 평가하는 경우가 많습니다.&#x20;

## 4. 골든셋과 일반 테스트의 차이

| 구분 | 일반 테스트           | 골든셋                |
| -- | ---------------- | ------------------ |
| 목적 | 소프트웨어 기능 검증      | 에이전트 수행 능력 평가      |
| 대상 | 코드의 동작           | 작업 지시부터 결과까지       |
| 입력 | 함수 인자, HTTP 요청 등 | 자연어 지시 + 코드베이스     |
| 결과 | 테스트 성공/실패        | 작업 성공률, 회귀 발생 여부 등 |
| 활용 | CI/CD, 배포 검증     | 모델·프롬프트·도구 변경 비교   |

골든셋은 기존 테스트와 경쟁하는 개념이 아닙니다. 기존 단위 테스트와 통합 테스트를 골든셋의 채점 도구로 활용할 수 있습니다.

또한 골든셋의 가치는 검증된 정답 기준에 있습니다. 단순히 임의의 작업 100개를 모았다고 신뢰할 수 있는 골든셋이 되는 것은 아닙니다.&#x20;

## 5. 코딩 에이전트를 개발한다면 어떻게 활용할까?

Claude Code 또는 Codex를 사용하는 프로젝트라면 다음과 같이 구성하는 것을 추천합니다.

```
project/
├── src/
├── tests/
└── evals/
    ├── golden/
    │   ├── bugfix.jsonl
    │   ├── feature.jsonl
    │   ├── refactor.jsonl
    │   └── security.jsonl
    ├── evaluator.py
    └── results/
```

골든셋을 통해 다음과 같은 실험을 할 수 있습니다.

- `CLAUDE.md`를 변경했을 때 실제 코드 품질이 개선되었는가?
- Claude Code와 Codex 중 우리 프로젝트의 버그 수정에 더 적합한 에이전트는 무엇인가?
- 새로운 MCP 도구를 추가했을 때 작업 성공률이 높아졌는가?
- 에이전트가 버그는 해결했지만 기존 기능을 망가뜨리지는 않았는가?

특히 기존에 실패했던 실제 개발 작업을 골든셋에 추가하는 방식이 유용합니다. 같은 문제가 다시 발생하지 않는지 지속적으로 검증할 수 있기 때문입니다.

정리하면 세 가지 개념을 구분하면 됩니다.

- 골든셋(Golden Set): 무엇으로 평가할 것인가? → 검증된 문제와 정답 기준
- 평가 시스템(Eval Harness): 어떻게 평가할 것인가? → 실행, 테스트, 채점 자동화
- 벤치마크(Benchmark): 성능을 어떻게 비교할 것인가? → 공통 평가 과제와 측정 결과

결국 코딩 에이전트에서 골든셋을 만든다는 것은 "AI가 코딩을 잘하는 것 같다"라는 주관적인 판단을 "동일한 작업 30개 중 27개를 실제로 성공했다"라는 측정 가능한 결과로 바꾸는 작업입니다.
