# 프롬프트 엔지니어링 (Prompt Engineering)

> 언어 모델이 요구한 품질의 출력을 일관되게 내도록, 모델에 주는 입력(지시, 예시, 형식, 배경 정보)을 설계하고 시험하며 고치는 작업.

## 요약

- 프롬프트(prompt)는 모델에 주는 입력 전체이며, 프롬프트 엔지니어링은 이 입력을 설계하는 일이다.
- OpenAI 문서는 모델 출력이 비결정적이므로 이 작업이 기교(craft)와 시험을 함께 요구한다고 설명한다.
- 대표 기법으로 명확한 지시, 예시 제공, 역할 지정, 구조화 태그, 단계적 사고 유도가 있다.
- Anthropic 문서는 성공 기준과 그 기준을 시험할 방법을 먼저 갖추고 나서 프롬프트를 고치라고 안내한다.
- 모든 문제가 프롬프트로 풀리지는 않으며, 모델 교체가 지연과 비용 문제를 더 쉽게 풀기도 한다.

## 왜 필요한가

같은 모델이라도 입력이 모호하면 출력의 형식과 품질이 매번 달라진다. 모델의 가중치를 다시 학습(fine-tuning)하지 않고도 입력만 바꿔 동작을 조정할 수 있으므로, 입력을 체계적으로 다듬는 방법이 필요해졌다.

## 어떻게 동작하나

1. 성공 기준을 정한다. 무엇을 잘한 출력으로 볼지 먼저 적는다.
2. 기준을 시험할 방법을 만든다. 대표 입력과 판정 방법을 모은 평가 집합이 여기에 해당한다.
3. 첫 초안 프롬프트를 쓴다.
4. 평가 결과를 보고 지시, 예시, 형식을 고쳐 다시 시험한다.

자주 쓰는 기법은 다음과 같다.

| 기법 | 내용 |
| --- | --- |
| 명확한 지시 | 원하는 결과와 제약을 구체적으로 적는다 |
| 예시 제공 | 입력과 기대 출력의 쌍을 넣는다 ([few-shot-prompting](../few-shot-prompting/README.md)) |
| 지시만 제공 | 예시 없이 작업만 설명한다 ([zero-shot-prompting](../zero-shot-prompting/README.md)) |
| 역할 지정 | 모델에 전문가 등의 역할을 부여한다 ([role-prompting](../role-prompting/README.md)) |
| 상위 지침 | 대화 전체에 적용할 규칙을 별도 위치에 둔다 ([system-prompt](../system-prompt/README.md)) |

## 예시

같은 요청을 모호하게 쓴 경우와 구체적으로 쓴 경우다.

```text
모호함: 이 함수 좀 봐줘.
구체적: 아래 Python 함수에서 예외 처리가 빠진 곳을 찾아, 위치와 수정 제안을
        한 줄씩 목록으로 답하라. 코드는 고치지 말라.
```

## 에이전트 맥락

코딩 에이전트에서는 사용자가 직접 쓰는 요청문 외에 지침 파일, 도구 설명, 이전 대화 기록이 모두 모델 입력에 들어간다. 프롬프트 설계는 요청문 한 개에서 이 입력 묶음 전체로 범위가 넓어진다.

## 흔한 오해

- **프롬프트 엔지니어링은 마법의 문구를 찾는 일이 아니다.** 성공 기준을 정하고 시험하며 고치는 반복 작업이다.
- **컨텍스트 엔지니어링(context engineering)과 같은 말이 아니다.** Anthropic 의 엔지니어링 글은 컨텍스트 엔지니어링을 프롬프트 엔지니어링의 자연스러운 확장으로 설명한다. 프롬프트 엔지니어링은 지시문, 특히 시스템 프롬프트를 쓰고 정리하는 일에 초점을 두고, 컨텍스트 엔지니어링은 도구, 외부 데이터, 메시지 기록까지 포함해 추론 시점에 모델이 보는 토큰 전체를 관리하는 일을 가리킨다. 두 용어의 경계는 문서마다 다를 수 있어 이 설명은 Anthropic 의 구분이다.
- **프롬프트가 항상 해법은 아니다.** 지연이나 비용 문제는 다른 모델을 고르는 편이 쉬울 수 있다.
